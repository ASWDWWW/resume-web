## What this role typically requires

Design, implement, test, and ship software that solves a real problem. Typical bar: production code in a team codebase, code review, debugging, some ownership of a feature or service, and comfort across at least one of frontend, backend, or mobile.

## What you have done in this project

You designed, built, deployed, and iterated a live patient-facing website for nine months. That includes a ~2,000-line production React SPA, a later modular redesign with a small design system, a serverless contact API in Google Apps Script, Firebase Hosting with custom domain and cache headers, and integrations with ChARM Health (booking) and Gmail (inquiry workflow). You also owned content, SEO structured data, accessibility, and deployment documentation.

## How that work applies to Software Engineer

A general Software Engineer is hired to take an ambiguous need and turn it into working software in production. That is exactly what happened here: a healthcare practice needed a public site that educates patients, books appointments, captures inquiries, and stays findable in search. You made product calls (mobile Call + Book dock, crisis resources, hidden reviews), technical calls (SPA vs multi-page, GAS vs EmailJS, referrer behavior for the EHR allowlist), and operational calls (how the owners deploy). That is software engineering, not tutorial work.

## Gaps versus a typical hiring bar

The system is a marketing site, not a multi-service product. There is no database, auth, automated tests, CI, or team code review. Most SWE interviews will still ask data structures, debugging a failing service, and working in a shared codebase. This project proves you can ship; it does not prove you have operated large systems.
